# v2.14 Phase 2 — Targeted HyDE Bridging: FALSIFIED

> Date: 2026-05-23
> Cycle: v2.14 (post-tag, executed under user "full send" override for the v2.14.1-equivalent items)
> Status: **hypothesis falsified by mini-soak data; code-side infrastructure shipped opt-in only**

## 1. The hypothesis

From `docs/PLAN_V2.14.md` Phase 2 (Draft v0.3):

> Address the omlx embedder's per-doc regressions on German
> (`ATZ_Elektronik` -12.5pp R@1) and code-dense (`Python_Cookbook`
> -12.4pp, `IRJET` -12.5pp, `Hybrid_electric_vehicles` -12.6pp,
> `Greenhouse_Design` -12.5pp) content **at query time**, NOT by
> routing to multiple embedder collections.
>
> When the [query-intent] classifier flags `intent=code` or
> `intent=minority_language`, the retrieval path automatically sets
> `use_hyde=True` + `hyde_provider="vllm"` ... with a content-aware
> HyDE system prompt variant.
>
> **Acceptance**: Targeted HyDE on the 5 affected docs lifts R@1
> by ≥8pp vs the no-HyDE baseline.

## 2. What shipped (code-side infrastructure)

| Component | File |

byte-for-byte identical to v2.13.0. Phase 2 is opt-in for any caller
that wants to experiment.

## 3. Mini-soak measurement

**Fixture:** `output/soak/v2.14_p2_intent_hyde/work.jsonl` — 5
affected docs × 5 chunks × 2 generated queries (qwen-max) = **50
queries total**. Same retrieval stack as v2.13.0 production (omlx
embed + BM25 + RRF + ModernBERT rerank); only `auto_intent_hyde`
differs between variants.

**Headline result:**

| metric | BASELINE (no HyDE) | INTENT-HYDE | delta |
|---|---:|---:|---:|
| R@1 strict (chunk_id match) | 64.0% | 62.0% | **-2.0pp** |
| R@1 lax (doc + page match) | 64.0% | 62.0% | -2.0pp |
| R@5 doc (gold doc in top-5) | 96.0% | 96.0% | +0.0pp |

**Per-doc:**

| doc | baseline R@1 | intent-HyDE R@1 | intent fires |
|---|---:|---:|---:|
| ATZ_Elektronik_German | 70% | 60% | 4/10 |
| ArcGIS_Python_Cookbook | 50% | 50% | **0/10** |
| Greenhouse_Design | 40% | 40% | **0/10** |
| Hybrid_electric_vehicles | 80% | 80% | 1/10 |
| IRJET_Modeling_of_Solar_PV | 80% | 80% | **0/10** |

**Targeted subset (5 queries where classifier fired, all `minority_language`):**
- R@1 strict: 80% → **60%** (-20.0pp)
- Phase 2 acceptance bar: lift ≥+8pp → **FAIL by 28pp.**

## 4. Why the hypothesis falsified

Two independent failure modes converged:

### 4a. Classifier under-triggers on the affected docs

3 of the 5 affected docs (ArcGIS_Python_Cookbook, Greenhouse_Design,
IRJET_Modeling_of_Solar_PV) got **0 intent fires across 30 queries**.
These are English-content docs where queries are about the *subject
matter* (PV system modeling, greenhouse climate, ArcGIS workflows),
not about *code syntax* per se. Sample queries that didn't classify
as `code`:

- "What is the formula for calculating PV system output?"
- "How does greenhouse ventilation affect crop yield?"
- "How do I project a geographic layer in ArcGIS?"

These are domain queries on code-dense or technical-domain content
but contain none of the syntax-keyword signals the code-intent
heuristic looks for. The classifier is correctly rejecting them by
its own definition — the gap is in the hypothesis that "query-side
intent classification" maps to "doc-side content type."

### 4b. HyDE actively hurts on the queries it does fire on

For the 5 German queries where `minority_language` intent fired,
R@1 dropped 80% → 60% (-20pp). The omlx Qwen3-Embedding-8B-mxfp8 is
**multilingual** — it already handles English↔German cross-lingual
embedding well. Adding a German hypothetical answer via local 27B
HyDE introduces noise (model hallucination, paraphrase drift) that
**reduces** dense-similarity to the gold chunk rather than improving
it.

## 5. Implication for the original v2.13 P1 deficit

The 5 affected docs' R@1 deficits documented in
`docs/QUALITY_SNAPSHOT_2026-05-22_v2.13_p1_omlx.md` (German -12.5pp,
code-dense -12pp each) are **not addressable by query-time intent
classification + HyDE**. Two real options remain:

1. **Per-doc embedder routing** — explicitly rejected by the user
   pre-Phase-2 as "permanent architectural fragmentation /
   architectural entropy." Not pursued.
2. **Accept the per-doc deficit as a known limitation** of the
   multilingual single-embedder design. The aggregate
   omlx-vs-dashscope win is 6/6 axes positive; the per-doc deficits
   are documented and accepted.

The plan's Phase 2 risk row anticipated this outcome:

> Phase 2 targeted HyDE doesn't recover the -12.5pp R@1 deficit |
> Revisit per-doc embedder routing as Phase 2-bis with concrete
> "HyDE didn't suffice" evidence (not speculative)

We now have that concrete evidence. Phase 2-bis (per-doc routing)
remains rejected per the user's stance on architectural entropy.
**The deficit is accepted as a known property of the v2.13 embedder
swap.**

## 6. What the code-side infrastructure is good for

The opt-in `auto_intent_hyde` knob + classifier + intent-aware
prompts aren't wasted infrastructure even with this falsification:

- **Future experimentation**: if a different corpus or different
  embedder profile makes HyDE useful for specific query intents,
  the wiring is in place. Just flip `auto_intent_hyde=True`.
- **Different intent definitions**: the classifier API
  (`classify_intent(query) -> str | None`) is extensible. v2.15 could
  add other intent classes (e.g., `intent="number_lookup"`,
  `intent="comparison"`) and bind them to different HyDE prompts or
  retrieval strategies without re-architecting.
- **Debug/diagnostic**: the per-query intent label is now available
  on every retrieval; downstream tools can use it for analytics
  ("how often do users query in non-English?").

The cost of keeping the code: ~250 LOC + 13 tests + 2 prompt
constants. Maintenance burden is low; default-off means zero
production behavior change.
